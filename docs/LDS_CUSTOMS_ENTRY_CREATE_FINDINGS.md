# LDS Customs Entry Create Findings

Last updated: 2026-06-04

## Goal

Create a brand-new `Customs Entry` in LDS from `andersoncb_erp` using only XML generated by our code and LDS manager `New()` templates, without reusing `raw_payload_xml` from an existing entry.

## What Is Confirmed

- LDS manager runtime URLs follow:

  ```text
  https://smstest.logisticaldatasolutions.com:8130/BrokerService/{ManagerName}
  ```

- WSDL/MEX metadata is available at:

  ```text
  http://smssystem.logisticaldatasolutions.com:8110/BrokerService/{ManagerName}/MEX
  ```

- `CustomsEntryManager.Save` is strict about `CustomsEntry` field order. Emitting fields in WSDL/XSD order fixed the earlier false validation failures such as:
  - `Importer required!`
  - `Carrier required!`

- The ERPNext submit builder no longer falls back to `raw_payload_xml` from existing entries.

- A generated-only header payload can be saved once into LDS. The resulting saved test entry is:
  - `EntryNumber = 30040158`
  - `Id = 1648`

## Critical LDS Behavior Discovered

The API-created row above is retrievable through:

```text
CustomsEntryManager.GetByNumber(0)
```

That means LDS persisted the row with internal document `Number = 0`.

After that row exists, every later API create attempt fails with:

```text
Cannot insert duplicate key row in object 'dbo.CustomsEntries' with unique index 'IX_Number'. The duplicate key value is (0).
```

This happens even when the payload is reduced to the smallest practical shape.

## Desktop vs API Comparison

Desktop-created entry:

- `EntryNumber = 30040521`
- `Id = 1670`
- `Number = 3004052`
- Persisted shape is very lean:
  - `Date`
  - `BondType`
  - `BrokerReferenceNumber`
  - `EntryFilerCode`
  - `EntryNumber`
  - `EntryType`
  - `Importer_Id`

API-created entry:

- `EntryNumber = 30040158`
- `Id = 1648`
- Still returned by `GetByNumber(0)`
- Persists richer header fields:
  - `Carrier_Id`
  - `ClientRef`
  - `DateOfArrival`
  - `DateOfImport`
  - `EstimatedEntryDate`
  - `PortOfEntry_Id`
  - `PortOfUnlading_Id`
  - `SuretyCode`
  - `TransportationMode`

However, mimicking the desktop row closely still does **not** fix the issue. Minimal API payloads that send only:

- `Date`
- `BondType`
- `BrokerReferenceNumber`
- `EntryFilerCode`
- `EntryNumber`
- `EntryType`
- `Importer_Id`

still fail with the same `IX_Number` duplicate-key error.

## Variants Already Tested

The following were tested against LDS `betatest` and did **not** resolve the issue:

- Header-only create with current generated payload
- Importer-only payloads
- Importer + `EntryType` only
- Sending `Importer_Id` only without an `Importer` navigation object
- Using importer `351` to match the desktop-created row
- Using importer `704` from our submitted test importer
- Changing `Number` to match `EntryNumber`
- Blanking `Number`
- Omitting `Number`
- Omitting `EntryNumber`
- Forcing `Id = 0`
- Blanking `EntityGuid`
- `CustomsEntryManager.New(sourceId)` instead of `New(null)`
- `Post(1648)`
- `Void(1648)`
- `UnVoid(1648)`
- `Delete` using the full entity returned by `GetByNumber(0)`
- Saving the `GetByNumber(0)` row back with a nonzero `Number`

## Other Useful Validation Learned

LDS enforces:

```text
BrokerReferenceNumber max length = 9
```

This should be enforced locally in ERPNext validation.

## Current Best Interpretation

The remaining gap is not basic XML shape, importer presence, or carrier presence.

The missing behavior is likely a lifecycle step or document-state transition that the LDS desktop client performs around create, and that a plain `CustomsEntryManager.New` + `Save` flow does not.

The strongest evidence is:

- desktop-created rows persist with a real internal `Number`
- API-created rows can persist, but remain reachable as `GetByNumber(0)`

## Recommended Next Step

Keep investigating the create lifecycle rather than shrinking the payload further.

Priority areas:

1. Identify the desktop-client step that moves a newly saved entry off internal `Number = 0`
2. Inspect whether another manager or post-save action is required before LDS finalizes the document number
3. Add local validation for `BrokerReferenceNumber <= 9`
